## 1. 결론

- **VBScript 종료 대응은 고도화의 타당한 이유입니다.** 다만 Windows 정책을 보면 당장 시급한 문제는 아니고, 정확한 일정은 Microsoft 원문으로 확인해야 합니다.
- **제안의 핵심 위험은 기능이 아니라 이관 범위입니다.** 맵 변환 방식, DLL 화면과 CX 컨트롤의 이관 방식, 15개 서비스의 의미가 불명확합니다.
- **상당수 개선 항목은 현재 AXIS에서도 시험하거나 구현할 수 있습니다.** 시세 병합, 지연 다운로드, GDI Scaling, WebView2, 조회 병합이 해당합니다.
- **권고:** 계약 전에 유료 PoC를 진행해 실제 화면으로 검증합니다. 그 결과로 플랫폼 교체와 AXIS 개선안을 비교합니다.

## 3. 항목별 검토

### 3.1 VBScript 종료

- 현재 화면은 `CLSIDFromProgID(L"VBScript", ...)`로 엔진을 씁니다. (`ibks/dll/vbs/scriptEngine.cpp`)
- 보도 기준 폐지 일정은 다음과 같습니다.
  - 1단계: Windows 24H2에서 선택적 기능(FoD), 기본 사용
  - 2단계: 2027년경 기본 비활성
  - 3단계: 시점 미정, DLL 제거
- 3단계 전까지는 선택적 기능을 켜는 것이 정상 경로입니다.
- `vbscript.dll`을 복사해 등록하는 방식은 기술적으로 가능성이 높지만 라이선스, 보안 패치, 시스템 충돌 문제로 권장하지 않습니다.

### 3.2 기동·로그인

- 제안서는 AS-IS를 "전체 리소스 선행 다운로드"라고 했지만, 실제로는 `infoAXIS`, `infoRSC`를 비교해 **변경 파일만** 받습니다.
- 파일 단위 증분 업데이트와 로컬 파일 보관은 이미 있습니다.
- `Workstation/DownloadOption` 값이 0보다 크면 `.map`을 화면 열 때 받습니다. 소스 검색 범위에는 이 값을 쓰는 코드가 없고, 검토 PC에서도 값이 없어 꺼져 있습니다. 고객 PC와 설치 프로그램은 미확인입니다.
- 스크립트 화면은 화면 열 때, exe와 DLL은 로그인 시점에 받는 구조가 합리적입니다.
- 남는 과제:
  - 화면 오픈 지연
  - 화면과 플랫폼의 버전 호환
  - 주문 화면의 구버전 차단
  - 장 시작 시 부하 집중
  - 화면 파일 서명 검증 (CRC는 변조 방지 수단이 아님)
- "로그인 창 3초"는 다운로드가 뒤로 밀린 값일 수 있으므로 측정 조건을 확인해야 합니다.

### 3.3 시세·멀티스레드

- 구조는 Mailbox, 컨트롤별 워커, 50ms 병합, UI 스레드 일괄 반영입니다.
- UPDATE는 키별 최신값, INSERT는 순서 보존 큐로 처리합니다.
- 비용의 대부분은 그리기라는 판단과 방향이 같습니다. "처리가 빠르다고 자주 그리는 것이 좋은 것은 아니다"라는 결론도 이 구조로 뒷받침됩니다.
- IB202700 `ParsingRTM`과 같은 계열입니다. 차이는 공통 컴포넌트 적용과 INSERT 큐 명시입니다.
- 제안서에서 맞지 않는 부분:
  - "수신·파싱·렌더링 멀티스레드"라고 하지만, 그림에서는 수신과 그리기가 UI 스레드입니다.
  - UI 스레드가 막히면 수신도 함께 막힙니다.
- 측정 자료의 한계:
  - Grid가 합계 약 88%로 전체의 약 68%입니다. 병합이 주 작업이라면 이 부하는 설명이 더 필요합니다.
  - Grid의 `Skip/s`는 0이고 `Backlog G:168`입니다.
  - 단일 스레드 비교값, 초당 건수, 표시 지연 수치가 없습니다.
- 스레드가 컨트롤별이면 화면이 늘수록 스레드도 늘어납니다.
- 시세마다 스크립트가 실행되면 JavaScript에서도 UI 병목이 남을 수 있습니다.
- 기존 DLL 화면과 CX 컨트롤에도 효과가 있는지 확인이 필요합니다.

### 3.4 DPI·모니터

- 현재 `axis.exe`는 DPI 미인식입니다. 매니페스트에 DPI 항목이 없습니다.
- exe 매니페스트의 DPI 설정은 프로세스 전체 DLL과 OCX에 적용됩니다.
- DPI 인식만 켜면 픽셀 기준 화면이 작아지고 레이아웃이 깨질 수 있습니다.
- "이상하게 작아지는" 증상은 호환성 재정의나 3rd Party 모듈의 영향일 수 있어, 먼저 해당 PC 상태를 봐야 합니다.

| 방식 | 화면별 수정 | 효과 |
|---|---|---|
| **GDI Scaling** | 거의 없음 | 글자와 선은 선명, 비트맵과 Direct2D는 그대로 |
| **Per-Monitor V2** | 맵은 플랫폼 중심(추정), DLL과 CX는 개별 수정 | 정확하지만 공수가 큼 |

- **권장:** 호환성 탭의 "시스템(고급)"으로 시험한 뒤 `AXIS/request_admin.manifest`에 `gdiScaling`을 추가합니다.
- 현재 매니페스트에 `supportedOS`가 없습니다. 동작 영향은 시험으로 확인해야 합니다.
- Per-Monitor V2는 `WM_DPICHANGED`로 폰트, 레이아웃, 비트맵을 실행 중에 다시 구성해야 합니다.
- 비트맵은 배율별 이미지보다 벡터, 9-slice, 고해상도 원본 축소를 우선 검토합니다.
- 다크모드까지 들어가면 이미지 수가 곱으로 늘 수 있습니다.

### 3.5 웹 연계

- CEF와 WebView2는 모두 Chromium 계열입니다.
- 제안서의 오픈소스 목록에는 CEF 89가 있어, CEF 방식일 가능성이 있습니다.
- 현재 HTS도 `CX_WEBEDGE`로 WebView2를 쓰고 있어, "IE 기반"은 절반만 맞습니다.
- `CX_WebLink(운영)`, `CX_NoticeWeb`, `cx_News`에는 IE 기반으로 보이는 코드가 남아 있습니다. 실제 사용 화면은 미확인입니다.
- **권장:** WebView2 유지를 기본안으로 합니다. CEF라면 Chromium 보안 패치 주기와 책임을 계약에 명시합니다.
- 브리지에는 허용 도메인과 허용 함수 목록이 필요합니다.

### 3.6 64bit

- 소스 하나로 Win32와 x64 빌드는 가능합니다.
- 그러나 AXIS는 포인터를 `long`과 `VTS_I4`로 넘기는 패턴이 있어 그대로는 안 됩니다. 예: `StartAxis`, `WriteDgram`, `CertifyId`
- 한 프로세스에는 32bit와 64bit 모듈을 섞을 수 없습니다.
- HTS에 로드되는 공급사 DLL과 OCX는 64bit가 필요합니다. 별도 프로세스 제품은 연동 모듈만 64bit이면 될 수 있습니다.
- 제안서상 3rd Party는 **연동은 제안사, 제공은 고객사**입니다. 모듈 확보와 비용은 IBK 몫이 될 가능성이 큽니다.
- 일정상 '27년 초에는 모듈이 있어야 합니다.
- 32bit와 64bit 병행은 빌드, 배포, 패치 목록, 테스트가 두 벌이 됩니다.
- 사인코리아 Windows 모듈의 비트 수도 함께 확인해야 합니다.

### 3.7 공통 라이브러리

- 정적 라이브러리는 사용하는 모듈 전부 재링크와 재배포가 필요합니다.
- DLL은 공개 인터페이스와 동작이 유지되면 DLL만 교체할 수 있습니다.
- 구조체, 클래스 멤버, vtable, 인라인, 매크로가 바뀌면 재빌드가 필요합니다.
- JavaScript 공통 모듈은 재빌드가 없지만, 호환성 오류를 화면을 열어야 발견할 수 있습니다.
- 공통 모듈의 버그는 전체 화면에 퍼지므로 영향 분석, 회귀 테스트, 롤백이 필요합니다.

### 3.8 스크립트 디버깅

- 일반적으로 V8 Inspector로 브레이크 포인트를 구현하고, 중단 시 호스트의 메시지 루프가 명령을 처리합니다.
- 중단 중 시세, 통신, 재진입 동작을 확인해야 합니다.
- 운영 배포본에서는 Inspector와 디버그 포트를 제거해야 합니다.

### 3.9 조회 데이터 캐싱

- 그림은 결과 캐시가 아니라 **진행 중인 동일 요청 병합**입니다.
- 종목이 같아도 TR, 입력, 조회 필드가 다르면 합칠 수 없습니다.
- 절감 효과는 현재 HTS 요청을 실측해 판단합니다.
- 주문, 잔고, 계좌 TR은 제외하고, 시세성 TR만 허용 목록으로 적용합니다.

### 3.10 3rd Party·행동분석·AI

- 범위에는 "도입 기반 마련"과 "연계 개발"로 표현되어 있습니다. 실제 분석 도구와 AI 서비스 제공 여부를 구분해야 합니다.
- 제품 구매, 라이선스, 데이터 처리 책임을 정리한 R&R 표가 필요합니다.

## 4. 주요 쟁점

1. **범위:** "15개 주요 서비스 재구축"과 "전 화면 이관"이 함께 있고, 15개 목록이 없습니다.
2. **맵 변환:** "자동 변환"이라고만 되어 있고 변환 방식과 변환율이 없습니다.
3. **DLL 화면과 CX 컨트롤:** 이관 방식과 수정 책임이 불명확합니다.
4. **서버:** 서버 계승이라고 하지만 Form Server, Meta DB, 사용자 설정 저장, API는 서버 작업이 필요합니다.
5. **오픈소스:** libpng 1.2.5, libjpeg 6b, zlib 1.1.4/1.2.3, CEF 89 등 구버전이 보입니다.
6. **소유권:** 소스 제공 범위와 공통 라이브러리, 빌드 환경 포함 여부가 불명확합니다.
7. **안정화:** 대규모 교체인데 상주 지원이 2주입니다.
8. **유지보수:** 8%에 제도 변경과 OS 대응이 포함되지 않습니다.
9. **성능 지표:** 3초, 5초, 5,000건, 멈춤 0건의 측정 조건이 없습니다.
10. **일정:** 범위 인벤토리가 착수 후 4주 내 확정이어서 계약 뒤에 범위가 바뀔 수 있습니다.

3. DLL 화면과 CX 컨트롤은 어떻게 이관하고, 범위와 비용에 포함됩니까?

### 성능

4. 3초, 5초, 5,000건, 멈춤 0건의 측정 조건과 PC 사양은 무엇입니까?
5. 패치가 있는 날의 시간도 측정 범위에 포함됩니까?
6. 단일 스레드 대비 CPU, 표시 지연, 처리량 비교 자료가 있습니까?
7. 워커의 작업 내용, 스레드 상한, Backlog 초과 시 처리, 데이터 유실 검증 방식은 무엇입니까?

9. 시세 멀티스레드가 자동 변환 화면, DLL 화면, CX 컨트롤에도 적용됩니까?

### 배포

10. 로그인 전, 로그인 중, 로그인 후에 각각 어떤 리소스를 받습니까?
11. 파일 내부 델타를 지원합니까? 다운로드 실패와 중단은 어떻게 복구합니까?
12. 화면별 최소 플랫폼 버전을 관리합니까? 주문 화면의 실패 정책은 무엇입니까?
13. 화면 파일의 서명 검증은 어떻게 합니까?

### 화면 환경

14. Per-Monitor V2를 지원합니까? 배율이 다른 듀얼 모니터로 시연할 수 있습니까?
15. DLL 화면, CX 컨트롤, 3rd Party 화면도 DPI 지원 범위에 들어갑니까?
16. 이미지 재제작이 범위에 포함되고, 벡터 아이콘을 지원합니까?
17. 웹뷰는 CEF입니까, WebView2입니까? 납품 버전과 보안 패치 주기는 무엇입니까?
18. 웹 브리지의 호출 권한은 어떻게 제한합니까?

### 64bit와 3rd Party
