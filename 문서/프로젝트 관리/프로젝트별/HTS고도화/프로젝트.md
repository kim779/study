- 목적: IBK투자증권 HTS(고객용/직원용) 고도화 사업 제안 대응. RFP 요구사항을 정리하고 현재 HTS(ibks) 대비 갭 분석 및 제안서 작성 준비
- 구분: 회사
- 관련 경로:
  - RFP 캡처 이미지: `HTS/1.JPG ~ 16.JPG` (제안요청서 2장 "제안 기본요건" ~ 3장 "유의사항". 1장 사업개요/목적 페이지는 없음)
  - 현행 HTS 소스/문서: `F:\src\IBK\src\ibks\docs\`

- 클라우드 서비스 제공 시 전자금융감독규정의 클라우드컴퓨팅 서비스 이용절차 충족

## 상세요건 (1~10)

### 1. HTS Client 개발 기본 요구사항
| 항목 | 요구 내용 |
|---|---|
| 실행/로그인 | 리소스 로딩 최적화로 초기 구동 시간 최소화, 간편인증 포함 다양한 로그인 지원 |
| 응답성/실시간 | 대량 시세 처리방식 적용, 화면 멈춤 없음 |
| 멀티윈도우/화면관리 | 다중 모니터 환경, 독립적 창 제어, 종료 시 기존 화면 저장 |
| 사용자 환경 저장/설정 | 화면배치, 관심종목, 컬럼, 정렬, 조건검색/차트설정, 주문설정, 환경설정 |
| 단축키 | 단축키 기능 제공 |
| 화면 간 연동 | 종목 선택 시 연동화면 동기화, 미연동 예외처리 |
| 팝업/알림 | 주문 체결, 가격 도달, 주요 공시 등 지능형 알림 |
| API 서비스 | 외부 알고리즘 매매/분석 도구가 HTS 데이터 및 주문에 안전 접근하는 전용 접속 모듈 |
| OS 비트 | Windows **64bit 기본**, **32bit 동시 지원** |
| 웹 컨텐츠 연계 | 임베디드 웹뷰로 공지/이벤트/서비스 화면 등 웹 기반 화면 사용 |
| 로그인 분리 | 고객용/직원용 로그인 화면 분리(혼용 방지) 설계·구현 |
| 외부 솔루션 | 보안, 차트, 조건검색, 모니터링 분석 툴 등 외부 솔루션을 플랫폼 내 안정 탑재·유기적 작동 보장 |

### 2. KRX/NXT 통합 대응
- 통합호가 및 개별시장(KRX, NXT) 각각 조회·연동 화면 제공
- NXT 거래시간 확대 및 신규 주문유형 포함, SOR/KRX/NXT 통합 환경 지원
- 시장 제도 변경 대응을 위해 **하드코딩 지양**, 신속 적용 가능한 구조 (거래시간 추가 연장, 신규 거래소 연동 용이)

### 3. 주문/업무 처리 안정성
- 일반 화면보다 높은 수준의 안정성
- 중복처리 방지, Timeout 처리, 전문 재처리 방안
- 네트워크 단절, 서버 장애, 체결 지연, 주문 지연, 비정상 응답 대응
- 장애 시 고객 안내 방안 (긴급 공지 알림 등 관리자 기능)

### 4. 통합검색
- 하나의 검색체계로 통합, 검색결과에서 해당 화면으로 직접 이동
- 검색대상: 종목, 화면, 메뉴, 뉴스, 공시, 상품, 투자정보 등

### 5. 금융상품 및 금융소비자보호
- 신규 금융상품 추가 시 전체 플랫폼 수정 없이 상품별 서비스 모듈만 추가하는 구조
- 온라인 금융상품 판매·설명 시스템 지원, 온라인 설명의무 가이드라인 중요사항 명확화·이해 지원, 이해 여부 확인 원칙을 시스템 설계에 반영

### 6. 관리자 기능
- HTS 운영 관리자 기능 구현, 권한 통제(IP통제 or 2-Factor 등) 강화
- 주요 기능: 긴급 공지 발송(개별/서버별/전체고객별), 웹 링크 관리, 영업일자 관리, 시스템별 모니터링 조회, 각종 통계 화면

### 7. 보안 요구사항
- 솔루션 제공: 공동인증, 사설인증, 통신구간 암호화, 이상거래 탐지 등
- 자체 보안요건: 접근통제, 권한관리, 개인정보 마스킹, 위변조 방지 등
- 취약점/악성코드 점검(IBK 수행) 발견사항 반드시 조치
- 사업기간 전반 감리(IBK 수행) 후 보완점 협의·조치

### 8. 성능 요구사항
- 단순 목표값이 아니라 **측정방법·검증방법까지 제시**
- Client 실행시간, 로그인 / 화면 내 지연 없음 (효율적 리소스 다운로드 방안)
- 화면 조회시간, 실시간 데이터 처리량 (관심종목, 종합화면, 현재가, 차트, 실시간잔고 등 다수 화면에서도 끊김 없이)
- PC CPU/Memory 자원을 충분히 활용할 수 있는 방안

### 9. 안정성 및 운영 효율성 강화
- 시스템 구조 및 소스코드 분석을 통한 유지보수 취약요소 개선
- 공통 기능·모듈의 표준화, 재사용 구조 적용
- 향후 기능 추가·변경을 고려한 확장 가능한 구조

- 제안발표(PT): 제안서 제출 순서의 역순, 제안사당 30분(설명 20분 + Q&A 10분). 발표자는 실제 투입 인력 중 총괄 최고책임자(PM 등), 이후 사업수행 기간에도 핵심 책임자로 참여. 발표자 변경 시 사전 승인 필요
- 평가: 기술 800점 + 가격 200점 = 1,000점. 평가위원회(당사 직원, 필요 시 외부전문가), 세부 배점 일부 조정 가능, 결과 비공개·이의제기 불가 (별첨6 평가기준(안) 참조)
- 협상 적격자: 기술능력평가 점수가 배점한도의 **85% 이상**인 자 중 점수순 협상순위 결정. 동점 시 기술평가 점수 높은 자 → 세부항목 배점 큰 항목 점수 높은 자 우선
- 계약: 협상에 의한 계약체결기준. 협상 불성립 시 차순위와 협상. 가격협상은 예산 이하에서 제안가격 기준, 제안내용 가감 시 상당 금액 조정

## 제안서 작성요령
- 목차: Ⅰ 제안개요(배경/목적, 범위, 특징·장점) · Ⅱ 제안업체 일반(일반현황, 주요사업실적 3년, 협력업체) · Ⅲ 사업수행부문(추진전략, 제안의 특징·장점, 세부계획(디자인/퍼블리싱)) · Ⅳ 사업관리 부문(일정/절차/관리방안, 수행조직·업무분장, 투입인력·이력, 보안준수계획) · Ⅴ 지원 부문(기타지원)
- 입찰가격 제안서는 별도 제출 (상세견적 및 산출근거 포함)
- 제안사별 표준양식으로 작성, RFP 요구사항과 부합해야 하며 미대응/상이 시 사유 명시
- 기술 경력사항 등 허위 기재 시 자동 탈락, 계약 파기 및 향후 참가자격 제한 가능
- 모호한 표현('고려', '추정', '예정' 등)은 평가 불가로 간주
- 제안서 내용은 계약서와 동일한 효력 (상충 시 계약서 우선). 변경은 당사 요청/승인에 따른 서면만 가능. 추가 제출 자료도 동일 효력
- 유의: 제출 서류 일체 반환 없음, 제안 관련 문서·내용 외부 누설 금지, 공식 절차 외 접촉/정보유출/부정행위 시 탈락 가능

## 확인 필요 사항 (IBK 질의 후보)
- 인포맥스 ASP 연계 방식 (웹뷰 임베드인지, 데이터 수신 후 자체 화면인지). RFP에 명시 없음
- 64bit 전환 범위: 기존 32bit OCX/외부 모듈(보안 솔루션, 차트 등)과의 호환 방침
- "API 서비스 지원 전용 접속 모듈"이 현행 OPEN API와 어떤 관계인지
- 공고일/마감일, 사업 예산, 사업기간
- RFP 1장(사업 개요·목적·범위) 원문 확보 (이미지에 없음)
