## OnClose() 코드 리뷰 (2026-07-15, 덤프 없이 소스 리뷰만으로 진행)

실제 종료 시 크래시 덤프가 아직 없어서, `AXIS/MainFrm.cpp`의 `CMainFrame::OnClose()`(약 335줄짜리 함수)를
소스 레벨로 리뷰해서 찾은 문제들. 아직 실제 크래시와 인과관계가 확인된 건 아니고, 구조적으로 위험한
패턴들을 먼저 제거한 것 — 다음 실제 덤프가 나오면 이 수정 이후에도 재발하는지가 핵심 검증 포인트.

1. **`m_hStopEvent` 이중 CloseHandle** (발견함, but 사용자가 "최근에 넣은 테스트 코드, 곧 삭제 예정"이라고
   확인 — 실제 원인 아닐 가능성 높음). 방법 B(중복 코드 제거)로 이미 적용됨.
2. **`OnClose()` 재진입 방지 없음** (수정 완료, 2026-07-15): `m_bClose`가 함수 맨 끝에서야 TRUE가 되던 걸
   맨 앞으로 옮기고 `if (m_bClose) return;` 가드 추가. `CExitD::DoModal()` 같은 모달 다이얼로그가 떠있는
   동안 메시지 펌프가 계속 돌아서, 그 사이 `WM_CLOSE`가 한 번 더 오면 `OnClose()`가 재진입되어 정리 코드가
   중첩 실행될 수 있었음. 단, 조기 리턴 3곳(`closeX()` 실패, 종료확인창 취소, 관심종목 처리 취소)에서는
   종료가 취소된 것이므로 `m_bClose = FALSE;`로 되돌려야 함 (안 그러면 이후 앱을 다시는 못 닫음) — 이것도
   사용자가 지적해서 함께 반영, 4곳 모두 적용 확인함.
3. **`OnTimer()`에 종료 중 가드 없음** (수정 예정, 사용자가 추가하기로 함): 이 클래스는 타이머가 20개 이상
   (`TM_IDLE`, `TM_AOS_ALIVE`, `TM_HISTORY`, `TM_MNGINFO`, `TM_AUTOHIDE` 등)인데 `OnClose()`는 그중
   `TM_SCRLOG`, `TM_PRNIMG` 딱 2개만 죽임. `OnClose()` 실행 중(모달창 등으로 꽤 걸림) 나머지 타이머가
   발동하면 이미 정리된 객체(자식창, `m_MClient->m_pBkMapWnd`, `m_wizard` DETACH 이후 등)를 건드릴 수
   있음. `OnSize()`에는 이미 `if (m_bClose) return;` 가드가 있는데 `OnTimer()`에는 빠져있어서, 같은 패턴
   추가를 제안함 — 위 2번 수정 덕분에 `m_bClose`가 `OnClose()` 시작과 동시에 TRUE가 되므로 이 가드
   하나로 모든 타이머를 한 번에 차단 가능.
4. **확인했지만 문제 없다고 판단한 것들**: `CBkWnd`(m_pBkMapWnd) 명시적 delete — `CBkWnd`는
   `PostNcDestroy` 오버라이드 없어 자가삭제 안 하므로 이중삭제 아님. `RemoveAllChild()` — 맵 정리만
   하고 포인터 접근 안 해서 안전. `m_wizard` — `CMainFrame` 생성 시 한 번 만들어져서 앱 종료까지
   명시적으로 delete되는 곳이 없음(소멸자 `~CMainFrame()`과 `OnDestroy()` 둘 다 거의 비어있어서 확인함,
   `m_mapHelper`/`m_axMisc`/`m_wizard` 등도 마찬가지) — 이건 메모리 누수 후보이긴 하나 프로세스 종료
   시 OS가 회수하므로 크래시 원인은 아닐 것으로 판단.

## 패치/모듈교체 시 axis.exe 자체종료 보장 (2026-07-21, 개발기 적용·확인 완료)

**배경**: HTS 종료 시 메모리 이슈와는 별개 건. axis.exe가 패치를 받을 때 `axisver.exe`를 띄우고
자신을 닫아야 하는데, 여러 이유로 axis.exe 프로세스가 제때 안 내려가서 axisver.exe가 패치 파일로
교체복사하는 과정에서 파일이 잠겨있어 복사가 안 되는 상황이 있었음. 패치/모듈복사/재실행이
번번히 발생하는 환경이라 우선순위 높게 처리.

**원인 분석**: `AXIS/axMisc.cpp`의 `CAxMisc::RunVers()`는 `axisver.exe`를 `CreateProcess()`로
띄우기만 하고 자기 자신(axis.exe)을 닫지 않음. 실제 종료는 axisver.exe가 되돌아와서 axis.exe
창(HWND)에 `WM_CLOSE`를 보내는 왕복 구조로 이루어지는데, axisver.exe 쪽(`ibks/dll/ver/axisver.cpp`
`updateObjectAXIS()`)의 `WaitForSingleObject(m_axis, 3000)`가 **HWND를 프로세스 HANDLE인 것처럼
잘못 넘기고 있어** 사실상 대기 없이 즉시 리턴 → `WM_CLOSE`만 던져놓고 axis.exe가 채 안 닫혔는데
바로 파일 복사를 시도해서 잠금 실패가 재현될 수 있는 구조였음. (이 axisver.exe 버그 자체는 소스가
`ibks/ver/`, `ibks/dll/ver/`, `src_7_11/platform/ver/` 세 트리에 나뉘어 있어 — 여러 트리 확인 필요
사안이라 — 이번엔 손대지 않고 axis.exe 쪽만 수정.)

**적용한 수정** (`AXIS/axMisc.cpp` `RunVers()`, `AXIS/MainFrm.h`, `AXIS/MainFrm.cpp` `OnTimer()`):
`type == verUPDATE`(패치)인 경우, axisver.exe를 띄운 직후 axis.exe가 axisver.exe의 `WM_CLOSE`를
기다리지 않고 **스스로 먼저** `PostMessage(WM_CLOSE)`로 정상종료(기존 `OnClose()` 경로, 재진입
방지 수정 포함)를 시도하고, 동시에 `TM_FORCE_TERMINATE`(3000ms) 워치독 타이머를 건다. `OnClose()`가
제때 안 끝나면 타이머가 발동해 `TerminateProcess(GetCurrentProcess(), 0)`으로 확실히 강제종료한다.
`verRETRY`/`verUSERID`(재로그인)는 건드리지 않음 — 파일복사가 없어 타이밍 이슈가 없고 정상 세션
종료가 더 중요하기 때문. 부수적으로 기존에 누수되던 `pi.hProcess`/`pi.hThread` 핸들도 같이 정리함.

**검증용 로그** (`Axis::home\exe\axis.log`, 기존 `WriteLog()` 사용):
- `[RunVers][verUPDATE] self-close start: ...` — watchdog armed 시점
- `[RunVers][verUPDATE] watchdog fired: ...` — 3초 내 정상종료 실패해서 강제종료 발동한 경우에만 찍힘

**개발기 실측 결과 (2026-07-21)**: `self-close start` 로그만 찍히고 `watchdog fired`는 안 찍힘 →
`OnClose()`가 3초 내 정상 종료 → 파일복사 및 재실행 정상 완료 확인. 강제종료 없이도 의도대로 동작.
사용자가 개발기에서 당분간 관찰하기로 함(패치 발생 빈도가 잦은 환경이라 반복 검증 목적).

**증상**: `ChartObject.dll` 내부에서 Access Violation **WRITE** (주소 `0x199cb03c`)

**콜스택**: `IBKCHART.OCX`(차트 컨트롤) `OnPaint` → `mfc140!COleControl::OnPaint` → `ChartObject.dll` 내부(함수명 미상, "CreateXScaleManager"는 가장 가까운 export일 뿐 실제 함수 아님)

**한계**: `ChartObject.dll`/`IBKCHART.OCX`에 맞는 PDB가 `D:\symbol`, `D:\symstore`, 로컬 빌드 어디에도 없음. 이 모듈도 symstore 자동등록 대상에 포함시키거나, 최소한 이 버전의 PDB를 확보해야 정확한 위치 특정 가능.
