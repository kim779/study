## 크래시 사례 #1 — khs779_71410h32m27s.dmp (2026-07-14 10:32 발생)

**증상**: Access Violation(0xc0000005), `VCRUNTIME140!memcpy` 내부에서 무효 포인터(`0x2343e000`) 읽기 시도

**추적된 호출 체인** (소스 코드 기준):
1. 시세 자동전환바 타이머 → `CBasebar0::OnTimer` → `Next()` → `ChangeMap()` (`DLL/sm/Basebar0.cpp`)
2. `axiscall()`(`AXIS/MainFrm.cpp`, AXI_CHANGEVIEW) → `CMapHelper::ChangeChild()`(`AXIS/MapHelper.cpp`) — Wizard 스크린 전환
3. `CfmCtrl::WriteData()`(`ibks/dll/form/fmCtrl.cpp`) — 종목코드 컨트롤(cx_codectrl OCX)에 값 전달, 동기 SendMessage
4. `cx_codectrl(운영)/ControlWnd.cpp`의 DLL_OUBx 핸들러 → VBScript 이벤트(OnChange 등) 동기 재귀 실행 (2~3단 중첩 확인)
5. 최종적으로 axis.exe 내부(함수명 미상)에서 memcpy 크래시

**해석**: 화면 자동전환 → Wizard 스크린의 VBScript 이벤트가 여러 겹 재귀 실행되는 도중 이미 무효화된 포인터를 읽음. 재진입 구조 자체가 근본 리스크로 보임.

**분석 중 발견한 문제 2가지**:
1. **PDB 불일치**: `D:\symbol\axis.pdb`가 이 크래시의 axis.exe 빌드(6/11)와 맞지 않아 axis.exe 자체 함수명은 확인 불가. symstore 버전관리 체계(`D:\symstore`)는 2026-06-26부터 이미 구축되어 있었으나, 이 빌드는 그 이전 것이라 소급 매칭 불가 — 6/26 이후 빌드부터는 정상 매칭 예상.
2. **덤프 타입 한계**: 크래시 당시 메모리(0x2343e000 부근)를 직접 확인하려 했으나, 이 덤프가 heap을 포함하지 않는 타입이라 조회 불가. → `AXIS/whdump.cpp`에 `MiniDumpWithIndirectlyReferencedMemory` 플래그 추가함(2026-07-14, 사용자 반영 완료) — 다음 크래시부터는 스택이 가리키는 힙 메모리도 확인 가능할 것으로 기대.

**상세 분석 원본**: `D:\src\IBKS\err\crash\khs779_71410h32m27s.analyze.txt`, `khs779_71410h32m27s.windbg_log.txt` (사용자 WinDbg GUI 교차검증, 동일 결과)

## 크래시 사례 #2 — xero2323_767h49m50s.dmp (실제 고객 덤프, 2026-07-06 발생)

**증상**: `ucrtbase!fwrite` 내부에서 Access Violation READ

**콜스택**: axSock(시세 소켓 OCX) 이벤트 → axWizard → `IB711100.DLL` → `PartnerMng.dll` → `fwrite()` 크래시

**확정된 근본 원인** (소스 코드로 특정, 신뢰도 높음):
`IBK_DRFN/ProjSrc/SrcDrfn/DrCommon/PartnerMng/_PartnerManager.cpp:1233~1253`,
`CPartnerManager::_DoPreReceiveData()`의 `TRNO_MSTCODE`(종목마스터) 처리부:
```cpp
char buf[8];
memcpy(buf, pData, 4);
int nTotCnt = atoi(buf);
nSize = nTotCnt * sizeof(MSTCode) + 4;   // 실제 수신 길이를 무시하고 데이터 내 카운트로 재계산 (미검증)
...
fwrite(pData, 1, nSize, fp);             // 재계산된 nSize만큼 읽음 → 실제 버퍼보다 크면 OOB read
```
호출부(`_PartnerManager.cpp:321`)에서 넘어온 `nLen`(실제 수신 바이트 수)을 검증 없이 데이터 내부 카운트값 기반 계산으로 덮어써서, 서버 응답이 예상과 다르면(네트워크 단편화/서버측 이슈 등) 버퍼 밖을 읽고 크래시.
**대응 방향(미정)**: `IBK_DRFN`이 사내 관리 코드인지 외부 제휴사 코드인지에 따라 직접 수정 여부 결정 필요 — 사용자 확인 대기 중.

## 크래시 사례 #3 — axis.exe.14196.dmp (2026-07-14 09:12 발생, Full Memory 덤프)

**증상**: `ChartObject.dll` 내부에서 Access Violation **WRITE** (주소 `0x199cb03c`)

**콜스택**: `IBKCHART.OCX`(차트 컨트롤) `OnPaint` → `mfc140!COleControl::OnPaint` → `ChartObject.dll` 내부(함수명 미상, "CreateXScaleManager"는 가장 가까운 export일 뿐 실제 함수 아님)

**확정 사실**: `!address 199cb03c` 조회 결과 **State=MEM_FREE, Protect=PAGE_NOACCESS** — 해당 주소는 크래시 시점에 할당되어 있지 않았음. 전형적인 **use-after-free(댕글링 포인터)** 패턴. `CXScaleManager`(차트 X축 스케일 관리, 순수가상 인터페이스, `IBK_DRFN/ProjSrc/SrcChartEx/ChartOCX/Include_Chart/Dll_Load/XScaleManager.h`)와 관련된 객체로 추정되나, 정확한 함수/라인은 특정 불가.

**한계**: `ChartObject.dll`/`IBKCHART.OCX`에 맞는 PDB가 `D:\symbol`, `D:\symstore`, 로컬 빌드 어디에도 없음. 이 모듈도 symstore 자동등록 대상에 포함시키거나, 최소한 이 버전의 PDB를 확보해야 정확한 위치 특정 가능.
