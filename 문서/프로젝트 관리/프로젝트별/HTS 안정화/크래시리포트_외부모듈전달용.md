## 이슈 #1 — PartnerMng.dll: 종목마스터(MSTCode) 처리 중 버퍼 초과 읽기 추정

### 요약

| 항목 | 내용 |
|---|---|
| 크래시 모듈 | `PartnerMng.dll` (File version 10.2.9.1, Timestamp 2026-03-18 09:51:41) |
| 예외 | Access Violation, **읽기(READ)**, `0xc0000005` |
| 크래시 지점 | `ucrtbase.dll!fwrite` 계열 내부 (`write_text_ansi_nolock`) — PartnerMng.dll이 호출한 `fwrite()` 안에서 발생 |
| 배포 경로(덤프 기준) | `C:\IBKS\IBK증권 HTS\dev\PartnerMng.dll` |
| 프로세스 | axis.exe (HTS 메인 GUI) |
| 트리거 상황(추정) | 종목마스터(MSTCode) TR 데이터 수신 처리 중 |

### 크래시 콜스택 (심볼 있는 부분만 발췌, 위→아래가 호출 순서)

```
axSock.ocx(시세소켓 OCX) 이벤트 발생
 → axWizard.ocx (내부 함수명 불명 — 심볼 없음)
 → IB711100.DLL (내부 함수명 불명 — 심볼 없음, SI050000 모듈)
 → PartnerMng.dll (내부 함수명 불명 — 심볼 없음)
 → ucrtbase.dll!fwrite → 크래시 (0x1dc38000 읽기 실패)
```
※ 스택에 보이는 `PartnerMng!SetPcTrInterface+0x7157` 같은 이름은 **가장 가까운 export 심볼일 뿐**, 실제 크래시 함수가 `SetPcTrInterface`라는 뜻이 아닙니다 (private PDB가 없어서 export 이름으로 대체 표시된 것). 정확한 함수명 확인을 위해서는 해당 빌드(Timestamp `69B9F71D`, CheckSum `0005545A`)의 PDB가 필요합니다.

### 원인 분석 (소스 코드 대조 결과 — 저희 쪽에서 소스를 보유하고 있어 확인 가능했음)

`PartnerMng.dll`은 `IBK_DRFN\ProjSrc\SrcDrfn\DrCommon\PartnerMng\_PartnerManager.cpp`로 빌드되는 것으로 파악됩니다. 아래 함수의 `TRNO_MSTCODE` 처리 분기에서 버퍼 크기 검증 없이 파일 쓰기를 시도하는 부분이 있습니다.

```cpp
// CPartnerManager::_DoPreReceiveData()  (_PartnerManager.cpp 약 1233~1253행)
else if(strcmp(szTRKey, TRNO_MSTCODE)==0)
{
    CString szFile;
    szFile.Format("%s\\%s", szDataDir, "MstCode.dat");

    char buf[8];
    memset(buf, 0x00, sizeof(buf));
    memcpy(buf, pData, 4);
    int nTotCnt = atoi(buf);

    nSize = nTotCnt * sizeof(MSTCode) + 4;   // ← 실제 수신한 데이터 길이(nSize 원래값)를
                                              //    무시하고, 데이터 내부의 카운트 필드로 재계산

    FILE* fp = fopen(szFile, "w");
    if(fp)
    {
        fwrite(pData, 1, nSize, fp);          // ← 재계산된 nSize만큼 pData를 읽어서 파일에 씀
        fclose(fp);
        ...
    }
}
```

**의심되는 문제점**:
- 이 함수를 호출하는 쪽(`_PartnerManager.cpp` 약 321행)에서 전달하는 `nSize`(원래 파라미터명)는 실제로 소켓/TR로 수신한 **실제 바이트 수**입니다.
- 그런데 `TRNO_MSTCODE` 분기에서는 이 값을 쓰지 않고, 수신 데이터의 앞 4바이트를 파싱한 `nTotCnt`(레코드 개수로 추정)를 이용해 `nSize`를 다시 계산합니다.
- 만약 `nTotCnt` 값이 실제로 수신된 바이트 수와 맞지 않는 경우(예: 네트워크 단편화로 일부만 수신, 서버 측에서 잘못된 카운트 전송, 데이터 파싱 오프셋 문제 등) `nSize`가 실제 버퍼 크기보다 커질 수 있고, 그 뒤 `fwrite(pData, 1, nSize, fp)`가 버퍼 범위를 넘어서 읽다가 Access Violation이 발생하는 것으로 보입니다.
- 저희가 확인한 크래시(읽기 위반, `fwrite` 내부)와 이 코드의 동작 패턴이 정확히 일치합니다.

### 요청 사항

1. 위 코드(`_DoPreReceiveData`, `TRNO_MSTCODE` 분기)에서 `nSize`(재계산값)가 원래 수신된 실제 바이트 수를 넘지 않는지 검증하는 로직이 있는지 확인 부탁드립니다. (현재 저희가 보유한 소스 기준으로는 검증 로직이 보이지 않습니다.)
2. `nTotCnt`가 비정상적으로 크거나 데이터가 예상 포맷과 다를 때 방어 코드(길이 상한 체크, 원본 수신 길이와의 비교) 추가를 검토 부탁드립니다.
3. 정확한 크래시 함수/라인 확인이 필요하시면 저희가 보유한 크래시 덤프(`xero2323_767h49m50s.dmp`)와 WinDbg 분석 결과(`xero2323_767h49m50s.analyze.txt`)를 전달드릴 수 있습니다.

## 이슈 #2 — ChartObject.dll / IBKCHART.OCX: 차트 그리기 중 use-after-free 추정

### 요약

| 항목 | 내용 |
|---|---|
| 크래시 모듈 | `ChartObject.dll`, `IBKCHART.OCX` (File/Product version **5.2006.9.15**, Timestamp 2025-10-17 11:04:11, CompanyName **dooriic**) |
| 예외 | Access Violation, **쓰기(WRITE)**, `0xc0000005`, 주소 `0x199cb03c` |
| 크래시 지점 | `ChartObject.dll` 내부 (정확한 함수명 불명 — 심볼 없음) |
| 배포 경로(덤프 기준) | `C:\IBKS\IBK증권 HTS\dev\ChartObject.dll`, `...\dev\IBKCHART.OCX` |
| 프로세스 | axis.exe (HTS 메인 GUI) |
| 트리거 상황 | 차트 컨트롤 다시 그리기(`OnPaint`) 도중 |

### 크래시 콜스택 (심볼 있는 부분만 발췌)

```
IBKCHART.OCX (차트 컨트롤) OnPaint 이벤트
 → mfc140!COleControl::OnPaint
 → ChartObject.dll 내부 (함수명 불명, "CreateXScaleManager"는 가장 가까운 export일 뿐 실제 크래시 함수 아님)
 → 크래시 (0x199cb03c 쓰기 실패)
```

### 원인 분석

크래시 주소(`0x199cb03c`)를 덤프 내에서 직접 조회한 결과, **해당 주소는 크래시 시점에 메모리가 전혀 할당되어 있지 않은 상태(MEM_FREE, PAGE_NOACCESS)** 였습니다. 즉 이미 해제된(또는 할당된 적 없는) 메모리 영역에 쓰기를 시도하다가 발생한 크래시로, **use-after-free(댕글링 포인터) 패턴**으로 판단됩니다.

크래시 지점이 export 심볼상 `CreateXScaleManager`(`CXScaleManager` 팩토리 함수, 차트의 X축 스케일 관리 객체 생성 함수) 근처인 것으로 보아, 차트 크기 변경/타임프레임 변경/화면 재생성 등의 시점에 `CXScaleManager`(또는 그 구현체) 객체가 해제된 이후에도, 그 객체를 참조하는 포인터가 `OnPaint` 경로에서 계속 사용되고 있을 가능성을 의심하고 있습니다. 다만 **저희 쪽에는 `ChartObject.dll`의 이 빌드에 해당하는 PDB가 없어, 정확한 함수/라인은 특정하지 못했습니다.**

### 요청 사항

1. **이 크래시가 발생한 정확한 빌드의 PDB 제공을 요청드립니다** — 아래 서명과 일치하는 PDB가 있으면 정확한 크래시 함수/라인 확인이 가능합니다.
   - `ChartObject.dll`: Timestamp `0x68F1A41B` (2025-10-17 11:04:11 UTC), CheckSum `0x000AF17E`, File version `5.2006.9.15`
   - `IBKCHART.OCX`: Timestamp `0x68F1A41B`, CheckSum `0x00098D30`, File version `5.2006.9.15`
2. 차트 리사이즈/타임프레임 변경/화면 파괴 시점에 `CXScaleManager` 구현 객체(또는 관련 내부 버퍼)의 해제 타이밍과, `OnPaint`/재도색 콜백에서 그 객체를 참조하는 코드 사이에 경합(레이스) 또는 해제 후 재사용 가능성이 있는지 점검 부탁드립니다.
3. 필요하시면 크래시 덤프(`axis.exe.14196.dmp`, Full Memory 포함이라 분석에 유리)와 분석 결과(`axis.exe.14196.analyze.txt`)를 전달드릴 수 있습니다.
